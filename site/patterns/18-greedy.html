Pattern 18 of 24

Greedy

Make the choice that looks best right now, never look back, and still end up optimal. Greedy is the fastest pattern there is, and the hard part is convincing yourself the local choice can never hurt.

1. What is this pattern for?

Giving change with the fewest coins: always hand over the biggest coin that still fits (25¢, then 10¢, then 5¢…). You never reconsider a coin you already gave. With normal coin systems this simple rule is optimal; with strange coins (1, 3, 4 for 6) it isn't, and that's exactly the point to check before trusting greedy.

A greedy algorithm builds the answer step by step, taking the locally best option each time and never undoing it. When it works, it's usually a single O(n) pass (often after an O(n log n) sort) with O(1) extra state. It works when a problem has the greedy-choice property: some optimal solution starts with the greedy choice, so making it never closes the door on the best answer. Typical shapes:

  • Reachability: keep only the farthest point you can reach (Jump Game).
  • Reset on failure: if a running total goes negative, nothing before can be the start (Gas Station, Kadane).
  • Take every gain: sum all positive increments (Stock II).
  • Sort, then decide: by end time (intervals), by size (boats), by rank (H-Index).
  • Two passes: satisfy constraints from the left, then from the right (Candy).

2. How it works (bisected)

  1. Find the local rule. What single decision can you make about the current element using only a few numbers you carry along (a maximum, a running sum, a count)?
  2. Argue it is safe. Show that any optimal answer can be changed to agree with your choice without getting worse (an exchange argument), or that the choice keeps every future option open.
  3. Sort if order matters. Many greedy rules only make sense in a particular order (by end time, by value).
  4. One pass, constant state. Update the carried numbers per element and read off the answer.
  5. Test a counter-example. If you can find a small input where the local choice loses, switch to Dynamic Programming.

3. Seeing a problem: how to spot Greedy

Trigger words

  • "can you reach the end", "minimum number of jumps"
  • "maximum profit with unlimited transactions"
  • "the minimum number of … to cover / to satisfy every …"
  • "circular route", "starting point that lets you finish"
  • "each child must get more than its neighbour", "assign at least one"

Shape of the input

  • An array where a decision at index i depends only on a summary of what came before (a max, a sum).
  • Items that can be sorted so the best next item is obvious.
  • Brute-force smell: trying every start, every subset or every split, when a single carried number would do.
The one question to ask"Can I decide this step using one number I carry, and can I argue that this choice never hurts later?" If you can't argue it, try DP instead.

4. When to use it, and when not to

Use Greedy when…Prefer something else when…
A local choice provably never blocks the optimum (exchange argument)Choices interact and a small counter-example beats the local rule: Dynamic Programming (e.g. coin change with odd coins, House Robber)
You only need reachability or a running summaryYou must count all ways or list all solutions: DP or Backtracking
Sorting reveals the best next item (intervals by end, people by weight)The "best next" changes after every step: keep it in a heap (Top K)
Constraints come from two directions (left and right neighbours)Constraints form a general graph: topological sort or DP over an order

Cost: usually O(n), or O(n log n) with a sort; O(1) extra space apart from any sorted copy.

Greedy algorithms make the locally best choice and never undo it. def best_start(gas, cost):
    gain = [g - c for g, c in zip(gas, cost)]
    if sum(gain) < 0:
        return -1
    start, tank = 0, 0
    for i, g in enumerate(gain):
        tank += g
        if tank < 0:
            start, tank = i + 1, 0
    return start

def min_candies(ratings):
    n = len(ratings)
    give = [1] * n
    for i in range(1, n):
        if ratings[i] > ratings[i - 1]:
            give[i] = give[i - 1] + 1
    for i in range(n - 2, -1, -1):
        if ratings[i] > ratings[i + 1]:
            give[i] = max(give[i], give[i + 1] + 1)
    return sum(give)
function minCandies(ratings: number[]): number {
  const n = ratings.length;
  const give: number[] = new Array(n).fill(1);
  for (let i = 1; i < n; i++) {
    if (ratings[i] > ratings[i - 1]) give[i] = give[i - 1] + 1;
  }
  for (let i = n - 2; i >= 0; i--) {
    if (ratings[i] > ratings[i + 1]) give[i] = Math.max(give[i], give[i + 1] + 1);
  }
  return give.reduce((s, x) => s + x, 0);
}

6. How to remember it forever

Memory hook: "Biggest coin that fits"Hand over the best piece now and never take it back, but only after checking that no weird coin system can trick you.
How this hook works: what “Biggest coin that fits” means

What the slogan means, phrase by phrase

“Biggest coin that fits”
At each step take the choice that looks best right now, like handing over the largest coin that doesn't overshoot.
“never take it back”
No backtracking and no table, just one pass. That's why greedy is fast and simple.
“but only after checking that no weird coin system can trick you”
Greedy is only correct for some problems. Before trusting it, look for a small input where the best-now choice loses.

Why this picture fits the pattern: Greedy problems look like DP problems. The hook carries both halves: the move (best choice now, never undo) and the warning (prove it, or find a counterexample).

Watch it on numbers

Change for 63¢ with coins 25, 10, 5, 1, and then a weird coin system.

  1. 25 → 38 left, 25 → 13, 10 → 3, then 1, 1, 1. That's 6 coins, which is optimal.
  2. Weird coins [1, 3, 4], amount 6: greedy takes 4, 1, 1 = 3 coins, but 3 + 3 = 2 coins. Greedy loses, so this is a DP problem (Coin Change 322).
  3. Jump Game [2, 3, 1, 1, 4]: the farthest reach grows 2 → 4 → 4 → 4, and index 4 is reachable, so True. On [3, 2, 1, 0, 4] the reach is stuck at 3 and index 4 is out of the light, so False.

The trap it saves you from

Trusting a greedy rule because it worked on the examples. Find the counter-example first. If one exists, switch to DP.

It still works when…

Non-overlapping intervals: always keep the meeting that ends earliest, which leaves the most room. Gas Station: when the running tank goes negative, no start in that stretch works, so restart after it.

Picture

A torch-bearer running forward: the light (farthest reach) only grows, and if you ever step out of the light you've failed.

Chant

Safety rule

"Find the counter-example first." Try 3–4 tiny inputs by hand; if greedy loses on one, it's a DP problem.

Problem: You start at index 0; nums[i] is the maximum jump length from index i. Return True if you can reach the last index.

Solve it on LeetCode ↗ · Video walkthrough ↗

Example 1
Input: nums = [2,3,1,1,4]
Output: true
Explanation: Jump 1 step from index 0 to 1, then 3 steps to the last index.
Example 2
Input: nums = [3,2,1,0,4]
Output: false
Explanation: You will always arrive at index 3 no matter what. Its maximum jump length is 0, which makes it impossible to reach the last index.

Constraints: 1 ≤ nums.length ≤ 10⁴ · 0 ≤ nums[i] ≤ 10⁵

Hint 1

If you can reach index i, you can reach every index before it too.

Hint 2

Keep the farthest reachable index; if the scan ever passes it, you're stuck.

From brute force to the pattern: DFS over all jump choices is exponential; a DP over "can I reach i?" is O(n²). Tracking only the farthest reach is O(n).

Spot it: A DP over "can I reach i?" works in O(n²), but the greedy view is O(n): everything up to the farthest index reached so far is reachable, so only that one number matters.

Approach:

  1. farthest = 0.
  2. Scan the indices left to right. If i > farthest, index i is unreachable and so is everything after it: return False.
  3. Otherwise extend farthest = max(farthest, i + nums[i]).
  4. If farthest reaches the last index, return True.
class Solution:
    def canJump(self, nums: List[int]) -> bool:
        farthest = 0          # every index up to here can be reached
        last = len(nums) - 1
        for i in range(len(nums)):
            if i > farthest:
                return False  # a gap: we can never get to i
            farthest = max(farthest, i + nums[i])
            if farthest >= last:
                return True
        return True

Problem: A circular route has stations; gas[i] is fuel available at i and cost[i] is fuel to drive from i to i + 1. Return the starting index that lets you drive one full lap with an initially empty tank, or -1. The answer is unique if it exists.

Solve it on LeetCode ↗ · Video walkthrough ↗

Example 1
Input: gas = [1,2,3,4,5], cost = [3,4,5,1,2]
Output: 3
Explanation: Start at station 3 (index 3) and fill up with 4 unit of gas. Your tank = 0 + 4 = 4 Travel to station 4. Your tank = 4 - 1 + 5 = 8 Travel to station 0. Your tank = 8 - 2 + 1 = 7 Travel to station 1. Your tank = 7 - 3 + 2 = 6 Travel to station 2. Your tank = 6 - 4 + 3 = 5 Travel to station 3. The cost is 5. Your gas is just enough to travel back to station 3. Therefore, return 3 as the starting index.
Example 2
Input: gas = [2,3,4], cost = [3,4,3]
Output: -1
Explanation: You can't start at station 0 or 1, as there is not enough gas to travel to the next station. Let's start at station 2 and fill up with 4 unit of gas. Your tank = 0 + 4 = 4 Travel to station 0. Your tank = 4 - 3 + 2 = 3 Travel to station 1. Your tank = 3 - 3 + 3 = 3 You cannot travel back to station 2, as it requires 4 unit of gas but you only have 3. Therefore, you can't travel around the circuit once no matter where you start.

Constraints: n == gas.length == cost.length · 1 ≤ n ≤ 10⁵ · 0 ≤ gas[i], cost[i] ≤ 10⁴ · The input is generated such that the answer is unique.

Hint 1

If the total gas is less than the total cost, no start works.

Hint 2

Drive once from station 0; when the tank goes negative at i, no station up to i can be the start, so restart at i + 1.

From brute force to the pattern: Trying every start and simulating a lap is O(n²). The reset rule rules out whole stretches of starts at once: O(n).

Spot it: Trying every start is O(n²). Two greedy facts make it O(n): (1) a lap is possible only if total gas ≥ total cost; (2) if starting at s you run dry before reaching j, then no start between s and j works either.

Approach:

  1. If sum(gas) < sum(cost), return -1.
  2. Drive once around from start = 0, keeping tank += gas[i] − cost[i].
  3. If tank drops below 0 at station i, restart: start = i + 1, tank = 0.
  4. The start left at the end is the answer.
class Solution:
    def canCompleteCircuit(self, gas: List[int], cost: List[int]) -> int:
        if sum(gas) < sum(cost):
            return -1             # not enough fuel in total for any start
        start = 0
        tank = 0
        for i in range(len(gas)):
            tank = tank + gas[i] - cost[i]
            if tank < 0:
                # we can't get past i from start, nor from any station in between
                start = i + 1
                tank = 0
        return start

        int tank = 0;
        for (int i = 0; i < gas.length; i++) {
            tank = tank + gas[i] - cost[i];
            if (tank < 0) {
                // we can't get past i from start, nor from any station in between
                start = i + 1;
                tank = 0;
            }
        }
        return start;
    }
}

What the code is doing, line by line:

  1. if sum(gas) < sum(cost): return -1: driving all the way around needs at least as much gas as the trip costs.
  2. tank = tank + gas[i] - cost[i]: fill up at i, then drive to i + 1.
  3. if tank < 0: we got stuck before i + 1. Any station between start and i would have arrived there with less fuel (it skips the non-negative stretch before it), so it would also get stuck. Jump to i + 1.
  4. return start: totals were enough, and this is the only start that never ran dry for the rest of the array. The part before it is covered by the surplus.

Constraints: 1 ≤ n == ratings.length ≤ 5 * 10⁴ · 0 ≤ ratings[i] ≤ 5 * 10⁴

Hint 1

Each child has two constraints: its left neighbour and its right neighbour.

Hint 2

Left-to-right pass for left neighbours, right-to-left pass for right neighbours, keeping the max.

From brute force to the pattern: Repeatedly fixing violations until none are left can take O(n²). Two directional passes satisfy both constraints minimally: O(n).

Spot it: Each child has two constraints (left and right). Satisfy them one direction at a time: a left-to-right pass fixes "more than my left neighbour", and a right-to-left pass fixes "more than my right neighbour" without breaking the first.

Approach:

  1. Start everyone at 1 candy.
  2. Left to right: if ratings[i] > ratings[i − 1], set candy[i] = candy[i − 1] + 1.
  3. Right to left: if ratings[i] > ratings[i + 1], set candy[i] = max(candy[i], candy[i + 1] + 1). Use max so the left rule stays satisfied.
  4. Return the sum.
class Solution:
    def candy(self, ratings: List[int]) -> int:
        n = len(ratings)
        candy = [1] * n
        # pass 1: beat the LEFT neighbour when rated higher
        for i in range(1, n):
            if ratings[i] > ratings[i - 1]:
                candy[i] = candy[i - 1] + 1
        # pass 2: beat the RIGHT neighbour too, without losing pass 1's guarantee
        for i in range(n - 2, -1, -1):
            if ratings[i] > ratings[i + 1]:
                candy[i] = max(candy[i], candy[i + 1] + 1)
        return sum(candy)

8. Common mistakes

Trusting greedy without a proofCoin Change with coins [1, 3, 4] and amount 6: "biggest coin first" gives 4+1+1 (3 coins), but 3+3 is 2 coins. When you can't argue safety, use DP.
Forgetting the global feasibility checkGas Station's reset trick only finds the right start if a full lap is possible at all. Check sum(gas) ≥ sum(cost) first.
One pass where two are neededCandy needs both neighbours satisfied. A single left-to-right pass misses decreasing runs like [3, 2, 1].
Overwriting in the second passIn Candy's right-to-left pass, use max(current, right + 1); assigning right + 1 can break the left-neighbour rule.
Sorting by the wrong keyInterval scheduling must sort by end time to keep the most room for later intervals; sorting by start time gives wrong answers.

Spot it: Sorting papers from most to least cited turns it into a greedy scan: the top h papers are the best candidates for an h-index of h, so keep increasing h while the h-th best paper still has at least h citations.

Problem: Return the maximum difference between successive elements in sorted order, in linear time.

Solve it on LeetCode ↗

Example 1
Input: nums = [3,6,9,1]
Output: 3
Explanation: The sorted form of the array is [1,3,6,9], either (3,6) or (6,9) has the maximum difference 3.
Example 2
Input: nums = [10]
Output: 0
Explanation: The array contains less than 2 elements, therefore return 0.

Constraints: 1 ≤ nums.length ≤ 10⁵ · 0 ≤ nums[i] ≤ 10⁹

Hint 1

The maximum gap is at least (max − min)/(n − 1).

Hint 2

Use buckets of about that width; where can the maximum gap be?

From brute force to the pattern: Sort and scan: O(n log n). Buckets: O(n).

Spot it: The answer is at least the average gap (max − min) / (n − 1). With buckets narrower than that, the max gap can't be inside a bucket, only between a bucket's max and the next non-empty bucket's min — a pigeonhole argument.

Why not another pattern? Sorting is O(n log n); the problem asks for linear time.

Approach:

  1. size = max(1, (hi − lo) // (n − 1)); bucket index (x − lo) // size.
  2. Keep min and max per bucket.
  3. Scan buckets in order: gap = bucket min − previous bucket max.
class Solution:
    def maximumGap(self, nums: List[int]) -> int:
        n = len(nums)
        if n < 2:
            return 0
        lo, hi = min(nums), max(nums)
        size = max(1, (hi - lo) // (n - 1))  # no bigger than the average gap
        count = (hi - lo) // size + 1
        bucket_min = [None] * count
        bucket_max = [None] * count
        for x in nums:
            b = (x - lo) // size
            bucket_min[b] = x if bucket_min[b] is None else min(bucket_min[b], x)
            bucket_max[b] = x if bucket_max[b] is None else max(bucket_max[b], x)
        best = 0
        prev_max = lo
        for b in range(count):
            if bucket_min[b] is not None:
                best = max(best, bucket_min[b] - prev_max)  # gap across empty space between buckets
                prev_max = bucket_max[b]
        return best

Explanation: Even if you activate all the four taps you cannot water the whole garden.

Constraints: 1 ≤ n ≤ 10⁴ · ranges.length == n + 1 · 0 ≤ ranges[i] ≤ 100

Hint 1

Each tap is an interval. You need to cover [0, n] with as few as possible.

Hint 2

This is like Jump Game II after computing the farthest reach from each position.

From brute force to the pattern: DP over positions is O(n · range); the greedy is O(n).

Spot it: Covering a segment with the fewest intervals → greedy interval jumping. Record, for each start, the farthest reach; then sweep like Jump Game II, opening a new tap when the current coverage ends.

Why not another pattern? DP over positions is O(n · range).

Approach:

  1. reach[l] = max(reach[l], r) for each tap (clamped to [0, n]).
  2. Sweep i = 0..n−1: track far; when i reaches end, open a tap (end = far); if far ≤ i, it's impossible.
class Solution:
    def minTaps(self, n: int, ranges: List[int]) -> int:
        reach = [0] * (n + 1)  # reach[l]: farthest point covered by a tap starting at or before... exactly l
        for i, r in enumerate(ranges):
            left, right = max(0, i - r), min(n, i + r)
            reach[left] = max(reach[left], right)
        taps = 0
        end = far = 0  # end: covered so far; far: best reach among taps starting <= i
        for i in range(n):
            far = max(far, reach[i])
            if i == end:
                if far <= i:
                    return -1  # nothing reaches past i
                taps += 1  # open the tap that reaches farthest
                end = far
        return taps

Hard 3948. Lexicographically Maximum MEX Array Amazon ArrayHash Set

Problem: Repeatedly remove a prefix of nums, appending its MEX to result. Return the lexicographically largest result.

Solve it on LeetCode ↗

Example 1
Input: nums = [0,1,0]
Output: [2,1]
Explanation: Take the first k = 2 elements [0, 1] which has MEX = 2. Current result = [2]. Remaining array [0] has MEX = 1. Thus, the final result = [2, 1].
Example 2
Input: nums = [1,0,2]
Output: [3]
Explanation: Take the first k = 3 elements [1, 0, 2] which has MEX = 3. nums is now empty. Thus, the final result = [3].

Constraints: 1 ≤ nums.length ≤ 10⁵ · 0 ≤ nums[i] ≤ 10⁵

Hint 1

What is the largest MEX any prefix of the remaining array can have?

Hint 2

Reach it with the shortest possible prefix.

From brute force to the pattern: All cutting choices are exponential; the greedy is linear.

Spot it: A prefix's MEX can't exceed the MEX of the whole remainder, so the best next value is the remainder's MEX. Reach it with the shortest prefix (greedy): that leaves the longest remainder, whose MEX (and length) can only be larger.

Why not another pattern? Trying all ways to cut the array is exponential.

Approach:

  1. suffix_mex[i] = MEX of nums[i:] (scan from the right, raising a pointer).
  2. At i: t = suffix_mex[i]. If t == 0, append 0 and take one element.
  3. Else scan forward until all of 0..t−1 are seen; append t and continue after that point.
class Solution:
    def maximumMEX(self, nums: List[int]) -> List[int]:
        n = len(nums)
        suffix_mex = [0] * (n + 1)
        present = set()
        mex = 0
        for i in range(n - 1, -1, -1):
            present.add(nums[i])
            while mex in present:
                mex += 1  # MEX only grows as the suffix grows
            suffix_mex[i] = mex
        result = []
        i = 0
        while i < n:
            target = suffix_mex[i]  # the best value we can append now
            if target == 0:
                result.append(0)
                i += 1  # shortest prefix: one element
                continue
            need = set(range(target))
            while need:
                need.discard(nums[i])  # collect 0..target-1
                i += 1
            result.append(target)
        return result
function maximumMEX(nums: number[]): number[] {
    const n = nums.length;
    const suffixMex: number[] = new Array(n + 1).fill(0);
    const present = new Set<number>();
    let mex = 0;
    for (let i = n - 1; i >= 0; i--) {
        present.add(nums[i]);
        while (present.has(mex)) {
            mex += 1;  // MEX only grows as the suffix grows
        }
        suffixMex[i] = mex;
    }
    const result: number[] = [];
    let i = 0;
    while (i < n) {
        const target = suffixMex[i];  // the best value we can append now
        if (target === 0) {
            result.push(0);
            i += 1;  // shortest prefix: one element
            continue;
        }
        const need = new Set(Array.from({ length: target }, (_, v) => v));
        while (need.size > 0) {
            need.delete(nums[i]);  // collect 0..target-1
            i += 1;
        }
        result.push(target);
    }
    return result;
}

                mex += 1;  // MEX only grows as the suffix grows
            }
            suffixMex[i] = mex;
        }
        List<Integer> result = new ArrayList<>();
        int i = 0;
        while (i < n) {
            int target = suffixMex[i];  // the best value we can append now
            if (target == 0) {
                result.add(0);
                i += 1;  // shortest prefix: one element
                continue;
            }
            Set<Integer> need = new HashSet<>();
            for (int v = 0; v < target; v++) {
                need.add(v);
            }
            while (!need.isEmpty()) {
                need.remove(nums[i]);  // collect 0..target-1
                i += 1;
            }
            result.add(target);
        }
        return result.stream().mapToInt(Integer::intValue).toArray();
    }
}

What the code is doing, line by line:

  1. MEX(prefix) ≤ MEX(remainder), since a missing value of the remainder is missing from the prefix too.
  2. Taking the shortest prefix that reaches it leaves a superset for later, which can only keep later values (and the length) at least as large.
  3. Each element is scanned once overall, plus O(target) work per step bounded by the elements consumed.

Medium 2680. Maximum OR Microsoft Array

Problem: Multiply elements by 2 at most k times in total. Maximise the OR of the array.

Solve it on LeetCode ↗

Example 1
Input: nums = [12,9], k = 1
Output: 30
Explanation: If we apply the operation to index 1, our new array nums will be equal to [12,18]. Thus, we return the bitwise or of 12 and 18, which is 30.
Example 2
Input: nums = [8,1,2], k = 2
Output: 35
Explanation: If we apply the operation twice on index 0, we yield a new array of [32,1,2]. Thus, we return 32|1|2 = 35.

Constraints: 1 ≤ nums.length ≤ 10⁵ · 1 ≤ nums[i] ≤ 10⁹ · 1 ≤ k ≤ 15

Hint 1

Should the doublings be spread out or concentrated?

Hint 2

For each candidate element, you need the OR of all the others.

From brute force to the pattern: Trying every distribution of k doublings is exponential; one element at a time is O(n).

Spot it: Greedy: shifting one number left by k pushes its highest bit higher than anything else can reach, so all k doublings go to a single element. Try each element, OR-ing it (shifted) with the prefix and suffix ORs of the rest.

Why not another pattern? Splitting doublings between elements never beats putting them all on the one that gets the highest bit.

Approach:

  1. prefix[i] = OR of nums[:i], suffix[i] = OR of nums[i+1:].
  2. Candidate prefix[i] | (nums[i] << k) | suffix[i]; take the max.
class Solution:
    def maximumOr(self, nums: List[int], k: int) -> int:
        n = len(nums)
        suffix = [0] * (n + 1)  # suffix[i]: OR of nums[i:]
        for i in range(n - 1, -1, -1):
            suffix[i] = suffix[i + 1] | nums[i]
        best = prefix = 0  # prefix: OR of nums[:i]
        for i, x in enumerate(nums):
            best = max(best, prefix | (x << k) | suffix[i + 1])  # all doublings on x
            prefix |= x
        return best
function maximumOr(nums: number[], k: number): number {
    // BigInt: x << k can pass 32 bits, where JavaScript's | and << would wrap
    const n = nums.length;
    const suffix: bigint[] = new Array(n + 1).fill(0n);  // suffix[i]: OR of nums[i:]
    for (let i = n - 1; i >= 0; i--) {
        suffix[i] = suffix[i + 1] | BigInt(nums[i]);
    }
    let best = 0n, prefix = 0n;  // prefix: OR of nums[:i]
    nums.forEach((x, i) => {
        const candidate = prefix | (BigInt(x) << BigInt(k)) | suffix[i + 1];  // all doublings on x
        if (candidate > best) {
            best = candidate;
        }
        prefix |= BigInt(x);
    });
    return Number(best);
}
class Solution {
    public long maximumOr(int[] nums, int k) {
        int n = nums.length;
        long[] suffix = new long[n + 1];  // suffix[i]: OR of nums[i:]
        for (int i = n - 1; i >= 0; i--) {
            suffix[i] = suffix[i + 1] | nums[i];
        }
        long best = 0, prefix = 0;  // prefix: OR of nums[:i]
        for (int i = 0; i < n; i++) {
            best = Math.max(best, prefix | ((long) nums[i] << k) | suffix[i + 1]);  // all doublings on x
            prefix |= nums[i];
        }
        return best;
    }
}

  1. The highest bit of the result decides most of its value; one element shifted by k reaches the highest possible bit.
  2. Prefix and suffix ORs give "everything except i" in O(1).

Medium 670. Maximum Swap Apple Math

Problem: Swap at most two digits once to make the largest possible number.

Solve it on LeetCode ↗

Example 1
Input: num = 2736
Output: 7236
Explanation: Swap the number 2 and the number 7.
Example 2
Input: num = 9973
Output: 9973
Explanation: No swap.

Constraints: 0 ≤ num ≤ 10⁸

Hint 1

Which position should you try to increase?

Hint 2

Swap it with the largest digit after it — which copy of that digit?

From brute force to the pattern: All pairs of positions is O(d²); the greedy is O(10d).

Spot it: Greedy: improve the leftmost position possible. For each digit from the left, if a bigger digit appears later, swap with the last occurrence of the biggest one (the last keeps smaller digits further left).

Why not another pattern? Trying all pairs of swaps is O(d²) — fine for 9 digits, but the greedy shows the reasoning.

Approach:

  1. last[d] = last index of digit d.
  2. For each position i: for d from 9 down to digit[i] + 1: if last[d] > i, swap and return.
  3. Otherwise the number is already maximal.
class Solution:
    def maximumSwap(self, num: int) -> int:
        digits = list(str(num))
        last = {int(d): i for i, d in enumerate(digits)}  # last position of each digit
        for i, d in enumerate(digits):
            for bigger in range(9, int(d), -1):
                if last.get(bigger, -1) > i:
                    j = last[bigger]  # the rightmost copy of the largest bigger digit
                    digits[i], digits[j] = digits[j], digits[i]
                    return int("".join(digits))
        return num  # already the largest arrangement reachable
function maximumSwap(num: number): number {
    const digits = [...String(num)];
    const last = new Map<number, number>();  // last position of each digit

    for (let i = 0; i < digits.length; i++) {

                const j = last.get(bigger)!;  // the rightmost copy of the largest bigger digit
                [digits[i], digits[j]] = [digits[j], digits[i]];
                return Number(digits.join(""));
            }
        }
    }
    return num;  // already the largest arrangement reachable
}

    public int maximumSwap(int num) {
        char[] digits = String.valueOf(num).toCharArray();
        int[] last = new int[10];  // last position of each digit (-1 = absent)

                    digits[j] = t;

                }
            }
        }

    }
